## How to work here
- Python: always `~/python/venvs/qbo311/bin/python3` by explicit path. Never `pip install` into it. Files in `~/python/config/` are secrets: never print them.
- After changing Python or templates: `sudo systemctl restart catalog-web`. Static files (`static/*.js`, `*.css`) need no restart, so a change to them is live the moment it is saved: test first. After changing a module the orders site imports: `sudo systemctl restart mmk-web`, and ask him first.
- A change to the Catalog.db schema: add the column in `db.init()`, run `manage.py init`, then restart, then `manage.py refresh`.
- Read-only reads of both QuickBooks companies and MMK are always allowed. Never trigger an MMK login from a script.
- No duplicated code: use the library in `~/python/qbo_scripts`; new shared functions go there, documented. Shared page helpers live in `static/common.js`. Every change to a product goes through `catalog_items.save()`.
- Changing product data or photos: tell him what you intend, then ask. A paste of a retailer's page or a picture address from him IS the go-ahead for that item.
- Testing anything that changes the site: copy the code, a backup of `Catalog.db` (SQLite backup call; the live file is in WAL mode), the photos and the catalog file to the session's scratch folder, add throwaway logins there, and drive it with Flask's test client or headless Playwright at 390 and 1280 px. Delete the copy afterwards. Never add test logins to the live database.
- Batch photo work: the server's Chromium runs `static/item.js` on a small page (see `CLAUDE.md`, "Photos"). Reset the file input between pictures, give each source file its own name, and never use `pkill -f` with a pattern that matches your own command line.
- Before telling him something cannot be done, cannot be read, or is not there, check it properly, and look at what a person would see (the page, the picture). Say "no match found", not "not on the store".
- Talk to him in plain language, conclusion first, real paths in commands. Record what he says about data and rules in his own words; do not stretch a short answer. When a decision changes, update the copy in `docs/` with a version bump and a change-log row, and tell him so the Project "Catalog" masters get the same update.
- When giving him a command to run: he may be on his Mac, where server paths do not exist. Say that it runs on the server.
- A list for Excel: comma-separated works. A long list to review: a private review page worked well (he approved two lists from one).
- When you name a SKU to him, give its name and say which system holds it.
- His Google Drive: the server's own rclone connection reads it (`rclone copy "gdrive:Catalog" <scratch folder>`). Name the folder; listing the top of the Drive is slow. Use it read-only.
- Retailer sites: a plain request is all that is ever used. shop.monseywine.com and simchaspirits.com pages read fine. KosherWine.com pages and columbuswines.com (pages and its own picture addresses) refuse automated requests: do not work around that; ask him to paste the page's text. Picture addresses on KosherWine.com and on a store's public picture server do read with a plain request.
- When a picture's label and the item's name disagree, stop and ask him before using it (the Shorr "Scarlett" / "Shikma" case); when two items share one source, say so.
