## 2. Requirements (decided)
- Customer-facing product catalog with ALL sellable products (~200 active), categories and real faceted filters.
- Purpose (clarified 2026-10-29): inform trade buyers what the product line looks like. Not retail selling. Speed matters more than print-quality imagery.

## 5. Data model

### Relationships
- BRAND 1—many WINE
- WINE 1—many LISTING
- STATE 1—many LISTING, PRICE_LIST, ACCOUNT, PROMOTION
- PRICE_LIST 1—many PRICE; LISTING 1—many PRICE
- PRICE_LIST 1—many ACCOUNT
- ACCOUNT 1—many USER, ORDER_REQUEST, ACCOUNT_TERM
- USER 1—many ORDER_REQUEST
- ORDER_REQUEST 1—many ORDER_LINE; LISTING 1—many ORDER_LINE

### Layer 1 — Product content (curated by Satla, shared across states; owned by the catalog database)
- BRAND: name, country, story, logo
- WINE: name; category (Wine, Spirits, Liqueur & Aperitif, Sake, Ready-to-Drink); type; style; sweetness; country; region; sub-region/appellation; grape/base (one or more); vintage (year or NV); abv; flags kosher (always yes), mevushal, kfp, organic; certifier (OU, OK, Star-K…); tasting_notes; photo; tech_sheet

### Layer 2 — State listings (Illinois sellable status from MMK; SKU, UPC and item ID from QuickBooks)
- STATE: code (IL, FL); qbo_company (realm ID — each state is its own QBO company)
- LISTING: sku (the key that ties MMK, QBO and the catalog together — Dovid confirmed 2026-11-10 that SKUs are identical in MMK and QuickBooks); mmk_sellable (Illinois listings only; checked daily; true when the item is in MMK — this is the Illinois gate); mmk_last_checked; qbo_item_id (synced; the ID in qbo.intuit.com/app/item?itemId=… — this ID is per QBO company, so a product sold in both states has a different ID in each); upc (synced); qbo_active (synced from QBO; informational only for Illinois; for Florida, existing in the Florida inventory is the gate); size, bottles_per_case; wine_id; show_in_catalog (hides deposits, freight, samples, and superseded duplicate SKUs)
- Exact MMK fields available (item identifier, status) to be confirmed when the MMK read is built.
- bottles_per_case is shown on the product page in the current release and comes from QuickBooks (decided 2026-11-12); which QuickBooks item field holds it is to confirm.

### Layer 3 — Trade & ordering
- PRICE_LIST: name (IL Retail, IL On-Premise, IL Chain…), state — mirrors how prices are organized in that state's QBO company (exact QBO mechanism to map during build)
- PRICE: price_list, listing, bottle_price, case_price — synced from QBO
- ACCOUNT: business_name, qbo_customer_id (synced), license_no, state, price_list, rep
- USER: email, role (trade, rep, admin), account (for trade users)
- ORDER_REQUEST: account, user, status (draft, submitted, in QBO), qbo_order_no
- ORDER_LINE: order_request, listing, cases, bottles (2026-11-13: Dovid sells no loose bottles; quantity is CASES only and may be a decimal such as 0.5, with a price per case; the bottles field is not needed)
- Current release (decided 2026-11-12): orders are EMAILED ONLY and not stored, so ORDER_REQUEST and ORDER_LINE are not used yet; they come into use when orders are inserted into QuickBooks or stored. The customer page shows address and contact, license_no, balance owed and rep, all read from QuickBooks; order history is QuickBooks invoices for the last 12 months with line items. All salesmen see all customers.

### Layer 4 — Special terms & promotions (PLACEHOLDERS — not defined yet)

- PROMOTION: company-wide offers for all customers in a state (examples given: "All rosé 20% off", "Buy 2 get 1 free"). Fields: state, name, description, active, start/end date. What it applies to and how the discount is calculated: TBD.

### Rules

## 5A. Data sources & daily reconciliation (decided 2026-11-10)
- Why a third store exists: QuickBooks item records have no proper place for grape, region, sweetness, certifier, Kosher for Passover, photos and so on, and IL/FL are two separate companies (shared content would be entered twice). The site also cannot read QBO or MMK live on every page view (too slow), and logins and order requests need a home. So the site reads its own database; scheduled jobs keep the copies current.
- Roles:

| System | Covers | Owns (edited there) | Catalog database's role |
|---|---|---|---|
| MMK (3PL for the Chicago branch) | Illinois only | What is sellable (item is in MMK = sellable) | Copy, refreshed daily — the Illinois gate |
| QuickBooks — Illinois company | Illinois | Prices, price lists, customers, QBO item IDs | Copy, refreshed by the sync |
| QuickBooks — Florida company | Florida | Prices, price lists, customers, QBO item IDs, and what is sellable (item exists in Florida inventory = sellable) | Copy, refreshed by the sync — also the Florida gate |
| Catalog database | Both | Photos, descriptions, filter fields, brand stories, logins, order requests, show/hide | Original — the only place it lives |

- Daily automated check: a scheduled job on the droplet reads MMK, both QBO companies and the catalog database every day, matches them on SKU (identical in MMK and QBO), updates the copies, and produces a mismatch report. No manual exports from any system.
- Illinois mismatch report (doubles as the tool for keeping MMK and QBO in sync):
  - In MMK but missing or unpriced in Illinois QBO → cannot be sold yet.
  - In MMK but no catalog content → needs photo and description.
  - In the catalog but no longer in MMK → hidden automatically.
  - In Illinois QBO (active) but not in MMK → listed for cleanup; never shown.
- Florida check (two-way): Florida inventory against the catalog database. Report: in Florida inventory but no catalog content → needs photo and description; in Florida inventory but unpriced → cannot be sold yet; in the catalog but no longer in Florida inventory → hidden automatically.
- How MMK will be read automatically: NOT yet settled. The droplet already has mmk_upload.py, which drives MMK through browser automation (Playwright/Chromium), so the likely route is the same technique reading MMK's item screen on a schedule. To confirm during build (see open questions).
- Proposed safeguard (not yet confirmed by Dovid): if a daily MMK read fails, keep the last known good sellable list and send an alert, rather than hiding the whole Illinois catalog.
- Initial load: the selling content in claude/Satla_Master_Catalog.csv is loaded into the catalog database once; after that it is maintained in the catalog's admin screen.
- Current release (2026-11-12): the daily check is NOT built yet. But the release does need to READ both QuickBooks companies for customers, balances, invoices, customer prices and bottles per case (consequence of Dovid's 2026-11-12 answers; see functional spec sections 3 and 4).
